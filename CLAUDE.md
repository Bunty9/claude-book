# CLAUDE.md

Guidance for Claude Code (and any agent) working in this repo. Read this before non-trivial work. For the long-form developer guide see [`docs/development.md`](docs/development.md).

## What this is

**Claude, End to End** — an interactive, offline-capable reference book that teaches Claude and Claude Code to three reader personas (beginner / engineer / automator). It is a **static-export Next.js SPA + PWA**: 53 MDX chapters, 11 interactive widgets, client-side search, per-reader progress and track selection. No backend, no database, no server runtime — it builds to a folder of static files served by Vercel.

- Repo: `github.com/Bunty9/claude-book` · branch `master`
- Prod: https://claude-book-one.vercel.app (Vercel, auto-deploys on push to `master` via the project's Git integration; manual prod deploy = `npx vercel deploy --prod --yes`)

## Stack

- **Next.js 16** App Router, `output: 'export'` (static SPA) — see the `@AGENTS.md` note: this is NOT the Next.js in your training data; check `node_modules/next/dist/docs/` when unsure.
- **React 19**, **TypeScript strict**, **pnpm**
- **Tailwind v4** (CSS-config via `@theme inline` in `globals.css` — there is no `tailwind.config.ts`) + `@tailwindcss/typography`
- **MDX** via `@next/mdx` (chapters are `.mdx`); **shiki** code highlighting; **mermaid** diagrams; **markmap** mind-maps
- **minisearch** for client-side search
- **@ducanh2912/next-pwa** for the service worker
- **vitest** + Testing Library (jsdom) — 380 tests / 24 files

## Hard rules

1. **TypeScript strict, no escape hatches.** No `as` casts, no non-null `!`, no `any`. Narrow with type guards (`in`, `typeof`, predicate functions) — see `MDXComponents.tsx` `hasCodeProps`/`isCodeElement` and `lib/track.ts` `isTrackId` for the established pattern.
2. **Never switch the build to Turbopack.** `pnpm build` must stay `next build --webpack`. The PWA plugin only injects the service worker on the webpack build; Turbopack silently skips it and `out/sw.js` disappears. After any build change, confirm `out/sw.js` exists.
3. **No secrets, tokens, client names, or PII** anywhere in the book content or code. This is a public repo and a public site.
4. **Git author must be `Bunty9 <cbipin2000@gmail.com>`.** Never add `Co-Authored-By`, "generated by", "assisted by AI", or any AI-attribution line to commits, PRs, or any public-facing content.
5. **Conventional commits** (`feat:`, `fix:`, `chore:`, `refactor:`).
6. **Keep state SSR-safe.** This statically exports, so every client store read must produce identical markup on the server snapshot and first hydration render. Use `useSyncExternalStore` (see `app/providers.tsx`), not lazy `useState` that reads `localStorage`. Do not call `setState` synchronously inside an effect — the react-hooks lint rule treats it as an error and it is the project's real gate.

## Architecture (how a page renders)

```
manifest.ts (chapter metadata, the source of truth)
        │
        ├─► app/(book)/c/[id]/page.tsx   generateStaticParams() → one static page per chapter
        │        │
        │        └─► chapterMdxRegistry.ts   id → lazy import('@/content/pN/slug.mdx')
        │                 │
        │                 └─► MDX rendered through MDXComponents.tsx
        │                          (pre→CodeBlock/shiki, <Mermaid>, <Quiz>, widgets…)
        │
        └─► scripts/build-search-index.mjs  strips MDX → public/search-bodies.json
                 │
                 └─► lib/searchData.ts + lib/searchIndex.ts  (minisearch, client-side)
```

- **`src/content/manifest.ts`** is the authoritative chapter list (id, title, part, per-track order, difficulty, minutes, tags, summary). Parts/labels in `src/content/parts.ts`; types in `src/content/types.ts`.
- **Three reader tracks** (`beginner`/`engineer`/`automator`) share one chapter pool; each chapter's `tracks` map gives its 1-based order within each track it belongs to. `chaptersForTrack(track)` derives the ordered list.
- **Progress + track** live in `localStorage` (`cb:progress`, `cb:track`, theme is `cb:theme`). Cross-component reactivity is via custom window events (`cb:progress`, `cb:track`, `cb:theme`) — writers dispatch, readers subscribe (`useProgressVersion`, `useSyncExternalStore`).
- **Routes:** `/` (home), `/start` (track picker), `/c/[id]/` (chapter; `trailingSlash: true`). The `(book)` route group provides the sidebar + TOC + topbar + search shell.

## Common tasks

### Add a chapter
Three edits, all required (a test enforces parity between them):
1. Add a `ChapterMeta` entry to `src/content/manifest.ts` (pick a unique `id`, set `part` + per-track order).
2. Create `src/content/pN/<id>.mdx`.
3. Register the lazy import in `src/app/(book)/c/[id]/chapterMdxRegistry.ts` (the import map is explicit on purpose so the static-export bundler can analyse every branch).

Then `pnpm build:search` (or just `pnpm build`) so search picks up the new body. `lib/chapterRegistry.test.ts` verifies every manifest id has a registry entry and vice-versa.

### Add an interactive widget
Pattern: **pure logic in `src/lib/<name>.ts` (unit-tested in `<name>.test.ts`), presentation in `src/components/widgets/<Name>.tsx`, registered in `src/components/MDXComponents.tsx`.** Keep all branching/scoring/graph logic in `lib` so it is testable without rendering; the widget is a thin client component over it. Then use `<Name />` directly in any `.mdx` file.

### Diagrams (Mermaid) — read before touching `Mermaid.tsx`
- Design tokens are authored in `oklch`; `getComputedStyle` normalizes them to `lab(...)` in this engine, which mermaid's color engine (khroma) cannot parse. `lib/labColor.ts` converts lab→rgb; `Mermaid.tsx` resolves every theme token through it. Do not pass raw CSS-var colors to mermaid.
- Mermaid is a global singleton. `Mermaid.tsx` serializes all `initialize`/`parse`/`render` through a module-level promise queue and re-initializes only when theme tokens change. Do not call `mermaid.initialize()` per-instance inside an effect — that reintroduces the multi-diagram race.

### Theming / design tokens
All color/spacing/radius tokens live in `src/design/tokens.css` (oklch, with a `.light` override block). `globals.css` maps them to Tailwind utilities via `@theme inline` (write `bg-bg`, `text-fg-muted`, `border-border`, etc. — never hardcode hex). Dark is default; the `.light` class is toggled on `<html>` by `providers.tsx` and pre-applied by a blocking script in `app/layout.tsx` to avoid a flash. `tokens.test.ts` guards token presence.

## Gotchas

- `out/sw.js` and `public/sw.js` / `public/workbox-*.js` are **build artifacts** — gitignored, do not commit.
- Inline `localStorage` access must be `typeof window === 'undefined'` guarded (static export prerenders on the server).
- The search body file is generated; never hand-edit `public/search-bodies.json`.
- `next-env.d.ts` is gitignored and regenerated — don't commit it.
- `<html>` carries `suppressHydrationWarning` because the pre-paint theme script mutates its class before React hydrates; keep it.
